## 目标和边界

新系统从独立仓库和独立数据目录开始，不把旧系统的运行时文件直接搬过来。普通对话优先使用 DSH 的 Agent、runtime、provider、会话恢复、插件加载和 Web 能力；用户访问公司项目、文件、知识库或企业插件时，再经过组织权限和审计链路。

默认模型配置为 DeepSeek 测试配置，但 provider、模型、能力标签和配额都由平台配置决定。浏览器永远不能直接看到模型 API Key、内部服务地址、数据库凭据或 DSH Home。

旧系统的代码会先按项目刷新到 GitLab 作为历史存档，数据库、上传文件、secret 和运行快照另行备份。新系统验证完成后才能执行旧系统切换和删除；删除命令不会写入仓库，也不会自动执行。

## 总体结构

```text
DSH Web 前端
       |
       v
API Gateway（SSO、租户上下文、限流、路由、审计）
       |
       +--> Agent Orchestrator --> DSH Adapter --> DSH runtime/provider
       |
       +--> Model Catalog / Secret Resolver
       +--> Plugin Host / Capability Broker
       +--> File & Artifact
       +--> Knowledge（PostgreSQL 元数据 + Milvus 向量 + Elasticsearch 可选）
       |
       +--> PostgreSQL（事务事实来源）
       +--> Redis（缓存、队列、租约、限流）
```

第一阶段保持模块化部署，先用一个 Gateway 和少量内部模块跑通端到端流程，再依据负载拆分容器。PostgreSQL、Redis 是核心依赖；Milvus/MinIO/etcd 和 Elasticsearch 通过 Compose profile 按需启用。

## 六项重点优化

### 1. 模型目录从环境变量升级为数据库策略

`platform.model_providers` 和新增的模型目录保存 provider、模型名称、能力（stream、tool、vision、embedding）、默认标记、组织范围、限额和状态。secret 只保存 `secret_ref`，真实 key 由部署环境的 secret 文件或密钥服务提供。

请求流程为：

1. Gateway 根据 SSO 用户和组织查出允许的模型目录。
2. 用目录中的 provider/model 做白名单校验，不接受浏览器自行注入的 base URL 或 key。
3. Model Gateway 按能力选择 DSH provider；平台 provider key 通过显式映射转换为 DSH provider 名称，没有对应 DSH 能力时才走平台兼容实现。
4. 每次模型选择写入审计和用量记录，默认模型只在目录中标记，不写死在业务代码。

初始种子数据可包含 DeepSeek 测试模型；生产启用其他 provider 前必须配置 secret 引用、TLS 地址、超时、限流和健康检查。

### 2. DSH 真实流式会话、恢复和上下文重建

`packages/dsh-adapter` 是唯一的 DSH 版本隔离层。Gateway 和业务插件不得直接导入 DSH SDK。Adapter 提供：

- 建立/恢复会话和显式 `DSH_HOME`、workspace 生命周期；
- `POST /v1/chat/run` 的 SSE 流式事件（token、tool、progress、error、done）；
- 客户端断线后的 resume、请求幂等键和重复提交保护；
- DSH runtime 进程退出诊断、超时、心跳、指数退避和最大重试次数；
- DSH 版本、profile、provider 和 runtime 可执行文件的启动自检。

每个会话的消息先写 PostgreSQL，再由 outbox 投递异步事件。恢复时以数据库消息和 DSH snapshot 为准，不把 Redis 当作唯一历史。模型请求出现不确定的 transport 错误时，默认标记为 `unknown`，由人工或幂等策略确认后再重试，避免重复扣费或重复执行工具。

### 3. 租户隔离和企业权限

所有组织相关记录带 `organization_id`；会话、消息、文件、插件授权、知识库文档和任务均通过用户所属组织过滤。数据库连接使用最小权限账号，生产可启用 PostgreSQL RLS；服务层仍必须进行权限检查。

权限判断顺序固定为：入口 SSO → 用户/组织解析 → 应用访问 → 资源 ACL → 插件 capability 权限。企业项目、企业文件和知识库请求不能仅凭前端字段判定；Gateway 需要从数据库和授权服务重新确认资源归属。

SSO 测试服只放在测试环境变量中，使用 HttpOnly Cookie、服务端 `query-user`、刷新和登出接口。测试服不可被复制成生产地址，认证上游异常返回 503 并记录 request id。

### 4. 审计、限流、任务重试和故障恢复

引入统一 `request_id`、`trace_id` 和 `idempotency_key`。审计事件记录用户、组织、动作、资源、结果、模型/provider、插件版本和耗时，但不记录 token、密钥、完整文件内容或完整提示词。

限流分三层：入口用户/组织限流、模型 provider 限流、插件 capability 限流。异步任务使用 PostgreSQL job 表或 Redis 队列，任务字段包括 `status`、`stage`、`attempts`、`max_attempts`、`locked_by`、`heartbeat_at`、`next_attempt_at` 和 `last_error`。租约超时可回收，重试采用指数退避并设上限；不可重试错误进入死信状态，供后台处理。

备份策略：PostgreSQL 定期逻辑备份加 WAL/物理备份（按公司要求选择），Redis 只作为可重建缓存，Milvus/MinIO/Elasticsearch 分别备份。每次版本发布前保存镜像 digest、迁移版本、Compose 文件和配置摘要，并至少演练一次恢复。

### 5. Linux 分阶段测试和可观测性

新系统固定使用独立前缀，例如 `/data/megmeet-ai-platform/`，以及独立 Compose project `megmeet-ai-new-test`、网络和 volume。测试分阶段：

1. `compose config`、镜像构建、迁移幂等和健康检查；
2. SSO 登录、组织权限、模型目录和 Gateway API；
3. DSH 无密钥启动、真实测试模型、SSE、resume 和超时恢复；
4. 插件安装、broker nonce、能力权限、幂等任务和产物下载；
5. 文件上传、知识库切片、Milvus 检索、Elasticsearch 可选索引；
6. 备份恢复、限流、审计查询和回滚演练。

每阶段都有明确的 PASS 证据、日志截断规则和失败处理。未通过的阶段不进入下一阶段；旧系统在整个测试期保持可回滚状态。

### 6. 原生 DSH 桌面前端和企业插件

桌面壳承载原生 DSH 的宿主、模块加载和 UI，企业能力通过受控扩展接入。旧 `apps/web` 自写 React 页面和发布脚本已退役；请求与历史摘要纯类型迁至 `packages/contracts/chat.ts`，原生 runtime 构建入口为 `dev-local/dsh`。原生企业插件选择器及执行桥接尚未实现，不能将纯类型迁移当作已经接通。

保持原生界面与普通聊天路径，在输入栏扩展点选择有权使用的企业插件，后端再次授权后路由业务任务。原生历史与 Gateway 平台历史当前是两条路径，统一关联和企业任务展示属于后续集成。企业能力作为带 manifest 的插件发布：版本、入口、输入/输出 schema、所需权限、租户范围、网络策略和回滚版本必须声明。插件通过 capability broker 调用文件、知识库、业务 API，不得直接读宿主 secret、数据库文件或任意内网地址。

历史保留策略支持全局、组织、项目和单会话四级覆盖，优先级为“单会话覆盖 > 项目 > 组织 > 全局默认”，至少包含保留天数、最大消息数、自动清理开关和法定保留标记。清理由可恢复任务执行并记录审计，不能把无限历史或 Redis 当成默认方案。

## 数据职责

| 组件 | 唯一职责 | 禁止承担 |
|---|---|---|
| PostgreSQL | 用户、组织、目录、会话、消息、插件、任务、审计元数据 | 不保存明文 API Key；不作为全文/向量索引 |
| Redis | 缓存、队列、短期锁、限流计数 | 不作为会话或权限唯一来源 |
| Milvus | 带租户过滤的向量索引 | 不保存权限事实和原文主记录 |
| Elasticsearch | 可选全文索引、脱敏运维搜索 | 不替代事务表 |
| MinIO/S3 | 文件和产物二进制 | 不绕过 Gateway 做下载授权 |

## 版本和配置管理

- Git 仓库只存代码、迁移、Compose、插件 manifest、配置示例和文档。
- `.env`、secret 文件、数据库卷、上传文件、模型 key 和证书均在仓库外管理。
- 镜像使用不可变版本标签和 digest；DSH SDK/runtime 版本写入发布清单。
- 所有数据库迁移可重复执行，破坏性迁移拆成“扩展 → 回填 → 切换 → 清理”多个版本。
- 测试、预发布、生产使用不同 Compose project、域名、secret 和数据库，不共用 volume。

## 从旧系统切换到新系统

### A. 备份与冻结

1. 将旧项目逐个整理并推送到 GitLab，保留原提交、tag、Dockerfile、Compose 和构建说明。
2. 在服务器外部保存 PostgreSQL、Redis（如需）、文件目录、Nginx 配置、secret 清单（不把 secret 内容放 Git）和 Docker 镜像 digest。
3. 记录旧系统容器、网络、volume、入口路由、数据量和回滚命令；停止自动发布。

### B. 新系统独立部署

1. 在 `/data/megmeet-ai-platform/releases/<version>` 解包 GitLab 版本。
2. 使用 `megmeet-ai-new-test` 项目名和独立卷启动 core；执行迁移和健康检查。
3. 按测试阶段逐项验收 SSO、普通 DSH 对话、企业权限、模型切换、插件、文件、知识库、审计和恢复。
4. 做一次真实备份恢复和 DSH transport 故障演练，保存验收报告。

### C. 切换与观察

1. 先在测试域名或测试路径接入新 Gateway，确认 Cookie、SSE、WebSocket/静态资源和错误码。
2. 选择少量测试组织灰度；观察模型错误率、延迟、队列积压、权限拒绝和资源占用。
3. 验收通过后切换正式入口到新 Nginx upstream，保留旧服务和旧卷只读观察窗口。

### D. 明确授权后的旧系统清理

旧系统清理是破坏性操作，必须满足：GitLab 存档可检出、数据备份可恢复、新系统观察窗口通过、回滚入口已演练、负责人明确确认。清理顺序为：

1. 停止旧 Compose 项目并确认新入口健康；
2. 移除旧容器和旧网络；
3. 将旧目录改名为带日期的归档目录，保留一个短期观察窗口；
4. 再删除旧目录和旧 Docker volumes；
5. 清理旧镜像、未使用网络和临时文件；
6. 复核磁盘、入口、备份恢复点和审计记录。

任何一步发现新系统异常，都先切回新旧入口中的已验证回滚点，不删除新系统数据。实际删除命令只在切换完成后由负责人现场确认执行。

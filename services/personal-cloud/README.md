# 每员工原生云端工作区

本目录的管理器是 r65 / DSH 0.2.1-rc.2 开发候选，尚未部署。公司当前仍使用 r62 / DSH 0.2.0-rc.2。网页通过它进入按员工隔离的云端 Host；桌面候选优先使用自己的本机 Host，企业能力桥按需访问服务器。具体正式版本见 [当前架构](../../CURRENT-ARCHITECTURE.md)。

## 身份、数据与资源

网关认证 IAM 身份后，使用稳定员工身份派生的 owner 标识调用私有管理器。普通请求不能指定员工、Docker 镜像、挂载或启动命令。每个 owner 的原生状态和工作文件保存在两只独立持久卷中；同一员工的多个对话不会各自新建一整套容器。

工作区限制为 1 CPU 配额、1.5 GiB 内存上限、512 进程/线程，启用 init 回收孤儿进程。容器使用 UID1000、只读系统根、移除 capabilities、禁止提权，不暴露 Docker socket。内存上限不是预先占用量。Office 共享服务是独立容器，拥有独立资源和进程预算。

最新已验证部署的 `PERSONAL_CLOUD_MAX_ACTIVE_HOSTS=0` 表示没有固定账号槽位上限，仍受启动并发和最低可用内存策略约束，不能理解为无限容量。关闭连接后计算环境保留 7200 秒；此保留期与登录期限、聊天及文件存储策略分别管理。仅保存历史聊天不会占用进程槽位，未退出的任务和进程会。

只有管理器持有 Docker socket，属于可信管理员边界，不应暴露给桌面、worker 或公网。worker 接收按身份和租约限定的模型调用能力，企业 IAM 密码、个人模型原始凭据及 SSH 密码不交给模型。

## 本分支的云端升级模块

`Dockerfile.manager` 将 `manager.py`、`runtime_admission.py`、`runtime_release.py`、`runtime_snapshot.py` 一起复制到镜像。CI 检查它们与 `native-upgrade/gateway/activation` 的被测代码完全一致。

- 新用户只有在两卷此前不存在、独占创建意图已持久化、两次独立空卷检查及所有权核验成功后才获准入；现有卷不会被猜测为空白新用户。
- 旧用户升级前必须停写，完整备份两卷并重新校验；全局激活只在原入口关闭、旧管理器保留且停止、新管理器唯一运行时进行。
- 恢复写入新的卷，原卷中新版数据保留。实际 manager 消费恢复映射；升级后新建而没有旧快照的用户不能被自动降回旧版。
- native021 的历史维护接口暂时关闭，包括整工作区清理；不能沿用旧删除/迁移逻辑破坏新准入回执。

39 项 Linux 测试和真实本机 Docker 合成卷流程已通过，不等于生产变更已获准入。接口、所需挂载、持久化保证及恢复限制详见 [RUNTIME-NATIVE021.md](RUNTIME-NATIVE021.md)。当前没有可直接执行的 r65 生产 apply 命令。

## 仍需完成的边界

生产切换需要核对实际基础镜像和配置、全量卷归属及备份容量，完成外层停写/服务替换/恢复事务，并验收 IAM、企业加密文件和业务任务。新旧镜像不能混用旧 `node_modules` 覆盖。正式桌面安装器和本地企业文件桥另行验收。

普通 Docker 卷不自动提供每员工硬磁盘配额；应结合数据盘容量、告警、备份和实际压测制定策略。r64 任务执行池尚未接管 DSH 工具，保持关闭；不得因本分支加入升级模块而自动放开远程执行或增加服务器。

较早的 `dev-local`、长沙部署、0.1.x Host、2 个活跃 Host 和 300 秒停机文档属于历史构建资料，不能据此判断当前线上策略。

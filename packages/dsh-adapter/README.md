# MEGMEET DSH adapter

This package is the version boundary for the Windows native DSH desktop. The
current executable uses the official npm runtime, **not the historical Python
SDK/wheel host**. Its npm-native-RPC SDK contract is declared explicitly.

`index.cjs` is canonical. The identical `desktop-local/dsh-adapter.cjs` copy is
generated by `desktop-local/scripts/verify-dsh-candidate.cjs --seal-local` and
bundled inside `app.asar`. No packaged app imports this repository directory.
Tests reject drift between the two copies.

## Responsibilities

- Exact 0.1.6-alpha.1 CLI/profile/model patch/startup authentication contract.
- Coherent runtime + native frontend + all236 DSH packages + Node24.13.0.
- MEGMEET branding revision5 + enterprise extension3.0.0 + workspace seam1.0.0.
- Runtime integrity, native resource verification, immutable data-format guard.
- Offline signed update **verification and staging**, without installation.

IAM, TokenKey, employee/department authorization and business plugin execution
do not belong here. `runtime-host.cjs` owns local networking/process lifetime;
the adapter supplies only the DSH-specific choices. Enterprise UI code remains
an independently maintained module (`dev-local/dsh/enterprise-native.mjs`),
injected through the version-guarded build overlay. Four small, explicit upstream
bundle adaptations remain: brand-slot occupant, hero wording/Preview, welcome
notice, and the pinned workspace slot/navigation feedback. The workspace adapter
binds both pristine input and adapted output hashes. An upstream byte mismatch
stops the build for review.

## Candidate verification

From repository root, after the normal adaptation refresh:

```powershell
& 'C:/Program Files/nodejs/node.exe' new-system/desktop-local/scripts/verify-dsh-candidate.cjs
& 'C:/Program Files/nodejs/node.exe' --test new-system/desktop-local/tests/dsh-adapter.test.cjs
```

The first command is read-only. It rejects mixed versions, missing modules,
altered frontend resources, missing extension/adaptation/asset metadata,
unrecognized adapter/API contracts and unsupported data format. Install and
Refresh scripts generate compatibility metadata only after complete static
validation; `verification: static-release-integrity-only` is deliberately not
a claim of real IAM, chat, history or server acceptance.

Existing runtime manifest fields remain. Added `compatibilitySha256` binds
`compatibility-manifest.json`, which binds adapter source, native/UI/SDK versions,
extension, package inventory, data and API contracts, Node and existing release/
adaptation/npm-lock fingerprints. A legacy build without this metadata needs the
controlled local sealing step; startup does not silently accept it.

## Signed updates

`signed-update.cjs` verifies an Ed25519 envelope against **separately pinned**
trusted public keys. It validates the exact signed payload, channel, increasing
sequence, expiry, artifact name/bytes/SHA256, compatible release set and native
data format. It can copy verified bytes into an exclusive candidate directory;
it never downloads, extracts, executes, replaces the running application,
modifies native history or claims installation success.

```powershell
node new-system/desktop-local/scripts/verify-signed-update.cjs signed-manifest.json trusted-policy.json MEGMEET-candidate.zip
node new-system/desktop-local/scripts/verify-signed-update.cjs signed-manifest.json trusted-policy.json MEGMEET-candidate.zip --stage D:/MEGMEET-updates
```

No production signing key, trust policy or signature is generated here. Tests
create ephemeral synthetic keys solely inside temporary fixtures. Automatic
update publishing needs a company signing identity, trusted key distribution,
monotonic installed-version state, a signed Windows installer and production
acceptance. This release remains an unsigned portable candidate. Checksums are
not signatures; this tool cannot upgrade an unsigned package into a trusted one.

See `docs/DSH-UPGRADE-AND-EXTENSION-BOUNDARY.md` for the release workflow.

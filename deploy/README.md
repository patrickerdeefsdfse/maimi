# 五机部署参考

网页入口的 `A1_GATEWAY_BACKEND`、`A2_GATEWAY_BACKEND` 需在每台应用服务器分别填写。对应本机的后端填 `gateway-entry` 的 Local ClusterIP 和端口 8080，另一台填对端应用服务器的业务地址和 NodePort 30080。两条路由均通过就绪检查后才接流，连接建立失败时切换到另一端。

发布身份见 server/release.json。这里的模板根据已审核的本地部署来源整理，并未导出当前集群全部资源。模板中的网络、卷、准入和数据库纪元需要由运维按站点实际情况配置。先替换所有占位符并在隔离环境做服务端 dry run。禁止直接向正式集群应用模板。

生产网关的首页手动下载使用 `MAIMI_WINDOWS_INSTALLER_SHARE_URL`。恢复时将模板中的 `SITE_WINDOWS_INSTALLER_SHARE_URL` 填为公司当前固定的钉钉文件 HTTPS 分享地址。桌面自动更新使用公司更新清单。

替换网关副本会沿用其 Deployment 中的分享地址、卷和挂载。恢复整套集群时，取同一发布点的 Deployment 和它引用的不可变 ConfigMap，并提供对应的已验证镜像。企业插件后台还需要已迁移至 030 的 PostgreSQL 数据库（含插件版本、授权、回执和审计）。用两个副本分别核对当前发布的模块摘要，经公司域名核对首页链接、更新清单和后台登录保护。历史模板及早期集群快照需要配合后续的发布和迁移记录使用。

包含 `serving_ready` 的管理器使用鉴权的 `GET /v1/ready` 做启动和就绪检查，`GET /v1/status` 继续向运维报告需要处理的工作区。两组探针随对应角色的代码一起切换。目录中引用 r106 镜像的历史模板保留该镜像支持的旧端点。

| 路径 | 设施和用途 |
| --- | --- |
| k3s | A1、A2、C 三个控制节点。Pod 网段按节点分配 /26，Pod 和 Service 各用独立完整网段，配置示例须与实际节点身份、网络和运行时接线核对 |
| kubernetes | 双副本网关、节点分散、管理与执行池、服务、监控 RBAC、网络策略结构 |
| postgres | B1/B2 Patroni、A1/B1/B2 独立协调服务、备份和监控历史表 |
| storage | NFS 业务文件挂载示例，现场设置路径、存储白名单、备份和 mount 单元名称 |
| entry | 两台 AP 的 HAProxy、keepalived、HTTPS 就绪探测和服务单元 |

先核验网络和持久盘，再配置 K3s 多数派、数据库主备和缓存、共享文件系统、管理程序和网关、AP/VIP、监控及恢复演练。统一域名、IAM、证书和私钥、SSH 主机身份、NAS ACL、模型与企业 API 授权均由现场管理。保留证书验证和必要的端口控制。

带 SITE_*_ENDPOINT 编号的条目代表不同网络策略或服务的目的地，应按所在规则的业务含义配置，禁止用宽泛 CIDR 替代。模板中的部分资源以 r96 清单为起点，现网后来有单独的地址、Pod 身份、存储和缓存纪元调整；不可把模板当作当次上线的完整实时快照。运行时工作区准入采用与镜像摘要匹配的不可变 ConfigMap。

B1/B2 的 Patroni 模板为带 configuration 与 required_private_fields 的描述对象，不能直接作为 Patroni 配置使用。由现场服务账号在私密目录生成最终配置，校验五个认证字段各自非空且来自明确授权的凭据文件。最终配置、WAL、数据库、证书、签名资料均不入 Git。watchdog 须在主机上确认设备和权限。异机备份需要独立介质及恢复演练。
